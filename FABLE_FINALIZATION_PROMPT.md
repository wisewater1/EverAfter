## 2. Strategic Decisions — Confirm With the User Before Large Changes

Do **not** silently pick an approach on these. Present the tradeoffs, get explicit user sign-off, then proceed. These are the two decisions with the largest blast radius:

### 2.1 Native iOS wrapper strategy (currently 0% started)

There is no Capacitor, React Native, Expo, Cordova, or Tauri dependency anywhere in `package.json`, no `ios/` directory, no `.xcodeproj`, no `capacitor.config.*`, no `app.json`/`metro.config.js`. The entire iOS effort starts from zero. Options to present to the user, with your recommendation and reasoning:

- **Capacitor wrap of the existing Vite/React SPA** (`npx cap init` / `npx cap add ios`, `webDir: dist`). Fastest path to a submittable build; reuses 100% of existing React code; gives native plugin access (HealthKit, push, camera) via Capacitor plugins/custom Swift bridges. Tradeoff: UI will read as "a website in a wrapper" unless native-feeling polish is added (safe-area handling, native nav gestures, native transitions), and Apple reviewers do sometimes reject thin webviews under Guideline 4.2 ("Minimum Functionality") if the app doesn't feel sufficiently native or doesn't use device capabilities.
- **React Native rewrite.** Better long-term native feel and HealthKit/push ergonomics, but is a ground-up UI rewrite of dozens of screens (`SaintsDashboard`, `RaphaelChat`, `CustomEngramsDashboard`, all the `st*` dashboards, vault, family tree, etc.) — multi-week/month effort, high risk of introducing new bugs, and effectively forks the frontend from the web codebase.
- **Expo (managed RN)** — same rewrite cost as RN, faster iteration/OTA updates, but similar scope as above.

**Your job:** propose Capacitor as the default recommendation (given timeline realism and the instruction to reach a finish line), explain why, but explicitly ask the user to confirm before you commit to the multi-day integration work of wiring `ios/`, signing, HealthKit bridge code, and push notifications. Do not start writing native Swift/Capacitor-plugin code until this is confirmed.

### 2.2 Stripe vs. Apple In-App Purchase conflict (Guideline 3.1.1)

Six recurring digital subscription tiers (Engram Premium, Health Premium, Insight Pro, Legacy Plus, Legacy Eternal, Ultimate Bundle — see `src/pages/Pricing.tsx:30-134`) sell exclusively through Stripe Checkout (`supabase.functions.invoke('stripe-checkout', { mode: 'subscription' })`, `Pricing.tsx:176-181`). EverAfter does not qualify for Apple's "reader app" exemption (it is not primarily a content-consumption app for previously-purchased content). Options to present:

- **Implement StoreKit/IAP** for all in-app-purchasable digital subscriptions in the native build, and reconcile entitlements between Apple's IAP receipts and the existing Stripe/Supabase `saints_subscriptions` table (dual-ledger problem — a user who subscribes via web/Stripe needs entitlement recognized in-app and vice versa, without double-charging).
- **Do not sell/upsell subscriptions inside the native app at all** — ship the iOS app as a companion to an account created and paid for via the web (still must not deep-link or instruct users to go pay elsewhere from inside the app, per 3.1.3 — this is the "external purchase" restriction, and is legally/policy risky without care).
- **Delay iOS submission** until IAP is properly built, if the user decides monetization parity is required at launch.

**Your job:** lay out the concrete cost/tradeoff of each (IAP integration is real engineering work — StoreKit 2 code, server-to-server receipt validation, reconciling plan state), and get explicit user direction before writing purchase-flow code for the native app. This decision also affects whether `Pricing.tsx` needs a native-specific variant.

Any other decision in this brief that materially changes product scope (e.g., cutting a feature that's currently fabricated, like deciding to remove the crypto WiseGold UI vs. building it for real) should also be surfaced to the user rather than assumed, per the same rule — see the "flag, don't silently decide" instruction repeated in relevant checklist items below.
